# CLEAR: technical and UX audit

Audit performed on 23 October 2026 against the actual implementation, its preserved mainnet corpus, current Solana documentation, browser interactions, and automated accessibility checks. This is an engineering review, not a security certification or a usability study.

## What the product should accomplish

The useful contribution is the continuous outcome → relationship → evidence workflow. Solscan already has balance changes, summaries, raw data, and a [TX Map](https://docs.solscan.io/transaction-details/transaction-details/tx-map). CLEAR should make those investigations easier to follow while keeping their technical limits visible. It should not turn an instruction’s requested amount into an unsupported claim about a wallet’s net receipt.

| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| RPC parsing          | The schema required parsed instructions to be objects, rejecting valid text/memo records. Nullable lookup data and omitted metadata were also too strict.                                                                         | Accept text/memo records, null loaded addresses, and unavailable metadata. Keep unsupported semantics inspectable. Dedicated parser regressions plus the real capture corpus.                                                                          |
| Token ownership      | If one owner field was absent, the other could be used to attribute the whole transaction to that owner. Authority changes were not shown explicitly.                                                                             | Preserve before/after owners. Classify ownership as stable, changed, or incomplete; do not assign ambiguous records to a wallet. Token-account perspective remains available.                                                                          |
| Token-2022           | Standard transfer labels could be mistaken for the amount actually received, and `transferCheckedWithFee` was omitted.                                                                                                            | Mark token edges as instruction amounts, retain mint/decimals and explicit fee amounts, and direct users to actual token-balance deltas. Gross amounts are not asserted to equal net receipt.                                                          |
| CPI evidence         | Missing stack height cannot establish a direct caller; failed inner-program logs can make a committed transfer interpretation unsafe. Later outer instructions after an execution error were also shown as attempted invocations. | Preserve unknown caller groupings, resolve known nested callers by stack height, conservatively withhold inner movement classification when failure logs make it uncertain, and label not-reached instructions as references.                          |
| Inspector            | Token evidence was accompanied by the token account’s native SOL before/after values, under unqualified labels.                                                                                                                   | Show the selected asset’s own units, symbol, decimal precision, and balances. | Transport            | HTTP-200 JSON-RPC errors, malformed envelopes, response IDs, and excessive response size were not fully distinguished.                                                                                                            | Validate envelope/version/ID/result presence, preserve exact integer lexemes, cap responses at 4 MiB, classify RPC throttling, redact provider messages, and set no-store/retry headers. | Transaction states   | Confirmed/finalized signatures with unavailable details could look pending; failed status lookup plus missing details could be called missing.                                                                                    | Distinguish processed/pending, confirmed-but-history-unavailable, truly absent provider records, and uncertain provider state. | Context continuity   | Refreshing a view lost the selected wallet and evidence.                                                                                                                                                                          | Validate and restore `layer`, `account`, and `focus` URL parameters; add a copy-link control. Reload/share-link browser tests retain the same evidence.                                                                                                |

Axe checks cover the main screens at desktop and mobile sizes.                                                                                     |

## Primary evidence behind the parsing decisions

- [getTransaction](https://solana.com/docs/rpc/http/gettransaction) returns transaction data and metadata, and can return null when a record is not available at the requested commitment.
- [RPC JSON structures](https://solana.com/docs/rpc/json-structures) distinguishes parsed and compiled instructions, lookup addresses, token balance account indices, owners, and exact atomic token amounts. Missing fields must not become invented balances or ownership.
- [Transaction introspection](https://solana.com/docs/core/transactions/transaction-introspection) describes outer/inner traces, lookup resolution, and optional stack heights. The implementation requests `jsonParsed`; it does not incorrectly feed those responses into a wire-transaction decoder.
- [Transaction execution](https://solana.com/docs/core/transactions) separates atomic execution outcomes from charged fees. The UI keeps execution success independent of finality.
- [Durable nonces](https://solana.com/docs/core/transactions/durable-nonces) documents that nonce advancement and fee effects can survive an execution failure. The app does not claim that absolutely every field reverts.
- [Token-2022 transfer fees](https://solana.com/docs/tokens/extensions/transfer-fees) explains that fee-bearing transfers can withhold tokens at the destination. Instruction amounts therefore are not treated as guaranteed net receipts.
- [getSignatureStatuses](https://solana.com/docs/rpc/http/getsignaturestatuses) supplies confirmation status independently of the transaction detail lookup.

## Added capabilities

Shareable investigation context; pasted explorer links with explicit network validation; paginated account history; account/history partial availability; address-comparison prefilling; persistent appearance preference; keyboard-safe mobile evidence inspection; automatic instruction-category selection; exact token-unit inspection; transport regressions; automated accessibility checks; and repository CI.

## Limits retained deliberately

Unknown protocols remain unknown. Funding is not automatically called refundable rent. Native SOL and wrapped SOL are not combined. Missing ownership is not guessed. A diagram does not prove recipient identity or safe ownership. Transaction summaries describe observed net changes rather than guaranteed intent. Recorded examples remain separate from live RPC lookups, and the minimal design transfer remains explicitly synthetic.

No measured usability improvement, exhaustive protocol parser, physical-device verification, security audit, hosted deployment, or actual Figma file is claimed. The Figma before/after screenshots and assembly checklist remain separate deliverables. See `TEST_EVIDENCE.md` for the exact checks completed on the final checkout.
